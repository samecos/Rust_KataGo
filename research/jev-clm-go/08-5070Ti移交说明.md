# RTX 5070 Ti 后续复测与移交

- `runs/2026-09-27-multitask-m5/benchmark-inputs.npz` 只含用户真实 19×19 自对弈局面的 32 行 `packed [N,22,46]` 和 `global_input [N,19]`，大小约 2 KB；提供与 M5 完全相同的计时输入，**不含训练目标**。来源是 `2026-08-20npzs.tgz` 中旧抽样清单的首个 NPZ，文件 SHA-256 为 `8639f83fa1ff3f4aa89ed1fd3b21d9f040647decdecf39e505c4a3e14aef0483`。该抽样的全部棋局已从新训练缓存排除。
- 原始 `2026-08-20npzs.tgz` 为用户提供，SHA-256：`b541cb0e499b03a9d4aaf180eab000f3855cede5281047d796ab6bf604a857dc`，约 910 MiB。它及 `data/`、`.venv/` 被本目录 `.gitignore` 排除；**若只用 Git 同步，不会带过去**。RTX **仅复测现成权重**时用上面的便携输入包即可；要重新准备缓存或训练，需另行复制原始归档并校验 SHA。

## 2. 在 RTX 上先复测同一对研究模型

在项目根目录为目标机创建独立 Python 环境，安装该机支持 CUDA 的 PyTorch 和 NumPy。先确认 `torch.cuda.is_available()` 为 `True`，并记录 PyTorch/CUDA/驱动版本和 GPU 名称。Mac 的 `.venv` 不能作为 Windows 环境复制。以下 PowerShell 用该机的 Python 路径替换 `<PYTHON>`：

```powershell
<PYTHON> research/jev-clm-go/benchmark_student.py `
  --dense-checkpoint research/jev-clm-go/runs/2026-09-27-multitask-m5/dense.pt `
  --compact-checkpoint research/jev-clm-go/runs/2026-09-27-multitask-m5/compact.pt `
  --input-pack research/jev-clm-go/runs/2026-09-27-multitask-m5/benchmark-inputs.npz `
  --output research/jev-clm-go/runs/5070ti-student-speed.json `
  --device cuda --batches 1,8,14,32 --rounds 5 --iterations 30 --warmup 10
```

脚本校验 checkpoint 身份、四头输出形状和有限值，逐次同步设备，交替 ABBA/BAAB 顺序，报告两种口径：设备驻留输入的**纯前向**、以及缓存打包输入的 CPU 解包→上传→四头前向→全部输出回传。JSON 包含原始计时块、输入及 checkpoint SHA。两种口径都不包括 NPZ 解压、合法着法过滤、搜索树或 Rust Worker 调度。

先比较同一 CUDA 设备上的 `dense` 与 `compact`，再与 M5 的**同机成对结果**并列展示；不能把跨硬件的绝对耗时相除当模型收益。若 5070 Ti 上轻量模型变慢，应如实保留负结果。

## 3. RustGo 现役模型后端需单独测

本目录的 `student_models.py` 只提供四个简化输出，和正式 TF3 v17 B11/B15 的层图、后处理、参数规模、棋力、plan 身份均不同。它们不能直接交给 `katago-rs nnbench --model`；本轮没有修改引擎、CUDA 后端或模型格式。本仓 [正式结项记录](../../docs/RustGo性能优化结项记录.md)给出的历史 Windows 交付身份是：`D:/Go/Server/models/kata1-tf3-b11c768-s11001M-d5973M.bin.gz`（SHA-256 `1881600caab9e9d85a3dd6a019e9b8e7d2c237b5f984e13ed49a8645be3077c6`）、`plans/worker-tf3-sm120-throughput.json`（SHA-256 `7910f765134322f264722c7533d659f5ee0f87828c48f444c3eb6cd1770dc7e4`）、`configs/worker_tf3_sm120_throughput.cfg` 和正式 Windows 二进制（SHA-256 `d218b98dfdf2eb75820465cbf625dfd3f690b91c3bb112f3be1a56d2cc644dcc`）。**本机 Git checkout 的同名 plan 是 LF 字节，实际 SHA 为 `a259247220b80f2e61cd24cd958f4b1b40202364c1862865cf765d3bbbb70959`；逐行换成 CRLF 后恰好得到历史 Windows SHA。**JSON 语义可能相同，但认证身份按实际字节核对。目标机必须先核对实际文件和 `cuda-fingerprint`，不能因为文件名相同就沿用认证身份。正式二进制位于 Git 忽略的 `target/`；若目标机没有它，新构建会有**新二进制身份**，不能直接沿用结项认证。

确认目标机实际模型、plan、二进制 SHA 与上述历史身份吻合，并确认配置仍是现役版本后，先记录该模型在认证 B14 范围内的 `nnbench eval` NN 吞吐。配置/plan 的最大物理 batch 是 **14**；`nnbench` 在 Benchmark 模式会以命令行最大 batch 初始化，因此不能把 `--batch 32` 与这份认证 B14 plan 搭配后称为现役基线：

```powershell
.\target\release\katago-rs.exe nnbench `
  --config configs/worker_tf3_sm120_throughput.cfg `
  --model D:/Go/Server/models/kata1-tf3-b11c768-s11001M-d5973M.bin.gz `
  --mode eval `
  --batch 1,8,14 --iterations 400
```

`eval` 走 `NnEvaluator` 的生产推理栈并能安装认证 plan，但默认 worker 数是每档 batch 的两倍，并非历史正式 Worker 的 C64；因此这条命令仍只是**现役模型与 plan 的独立 NN 对照**，不能复述成结项记录的 B14/S2/C64 Worker RPC/s。`nnbench --mode direct` 和 `kernel` **不能安装 `cudaTacticPlan`**，只适合不含认证 plan 的路径诊断；不能把它们当上述对照。正式 Worker 结果与调用口径见结项记录。PyTorch 脚本与这些口径仍不同。即使数字显示研究模型更快，也只说明**不同模型/执行栈的实验吞吐差异**，不能写作正式 RustGo 推理提速。要回答能否替换正式模型，还需同一新权重可被引擎加载的图和输出合同、整图数值金标、相同硬件 ABBA、等时间/等访问数对局。这属于之后另开明确授权的引擎/模型部署工作。
