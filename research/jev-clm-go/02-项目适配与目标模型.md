Windows 记录中的旧 ONNX v15 是 **75,008,575 参数**（[需求汇总](../../docs/需求汇总.md)）。现役原生 TF3 v17 B11 是 C768 级架构（[部署说明](../../docs/TF3权重适配与Worker部署.md)）；本 macOS checkout 无其权重，因此不能把旧 ONNX 精确参数数写成原生 v17 的精确计数。本文把「约 70–80M」作为 B11 量级**规划范围**，正式规模须在目标权重上通过 [`ModelDesc::get_num_parameters()`](../../crates/kata_nn/src/desc.rs) 计数。

## 2. 数据提供什么，还缺什么

[`TrainingWriteBuffers`](../../crates/kata_data/src/training.rs) 写出的无 metadata v7 行可包含：

- `binaryInputNCHWPacked`：`[N,22,46]`，每平面 361 位，按高位先行打包；`globalInputNC`：`[N,19]`。
- `policyTargetsNCMove`：`[N,2,362]`，当前和下一着的**搜索目标计数**。`globalTargetsNC[:,26]`、`[:,28]` 表示对应目标是否真实存在。计数为 0 **不等于非法着法**。
- `qValueTargetsNCMove`：`[N,3,362]`，候选的搜索 win-loss、score、访问数；值经过量化缩放，只有满足访问/稳定性门的候选才可用于难负例。不能把未搜索动作的 0 当负面质量标签。
- `globalTargetsNC`：`[N,64]`；`41:47` 六段存 128 位棋局哈希，`51` 为回合序号，`25` 为行权重，`62` 指示真实终局。按行随机分训练/测试会泄露同一棋局，须按棋局哈希切分。
- `valueTargetsNCHW`：`[N,5,19,19]`，第 2/3 通道是向前约 8/32 手的黑白占位（按当前行视角），`globalTargetsNC[:,33]` 表示未来棋盘监督可用。尾盘索引会截断至终局；它不是完整的未来规则/劫/历史状态。

字节预算由上述七个数组形状算得约 **7,611 B/行（解压后的原始数组总量）**，即 100 万行约 7.6 GB 十进制，不含压缩、索引、增强副本和训练激活。首份 tar 实际只有六数组、缺少 Q；新 `.tgz` 有 Q、混合 v2/v3 目标格式。两者均混有非 19 路行，须按[首份](05-真实数据试验.md)和[新包](06-八月归档复验.md)的显式门筛选。NPZ 行可能随机抽样并包含 side positions，不能仅凭棋局哈希和相邻回合号就声称得到完整合法变化序列。完整变化必须从棋谱/自对弈轨迹按规则重放并复核。[`training.rs`](../../crates/kata_data/src/training.rs)

## 3. 应用前景，按可行性排序

| 场景 | 预期价值与必要条件 | 当前判断 |
| --- | --- | --- |
| **训练期对比辅助目标** | 用状态—行动/变化对齐提升共享棋盘表征，最后保留完整 KataGo 输出；同计算量消融和棋力证明增益 | **优先研究**；可在独立训练管线做，正式加载仍须兼容权重导出 |
| 离线棋谱/自对弈候选变化重排 | 只评少数完整合法变化，检验 CLM 是否能区分战术质量；需要 PV/真实变化数据和可靠胜率/目差标签 | 可行的第二实验；不阻塞当前游戏运行 |
| 搜索根节点的候选变化校验 | 根节点少量调用，可能降低误选；需要 Server 接口、延迟预算及等时自对局 | **有条件的后续工程**；本轮无上线能力 |
| 用 CLM-8B 替代逐叶围棋 NN | 还需 policy/value/目差/ownership、棋盘表征、同卡性能和棋力 | **不作为目标** |
| 用 Jev 托管 API 决定每步或每叶 | 闭源权重、外部服务延迟、输入合同不匹配、无棋力证据 | 仅概念参照；不进入正式推理路径 |

两份真实归档的同预算探针显示：固定 362 着法的相似度头在第二份数据上[没有稳定胜过线性头](06-八月归档复验.md)。因此该固定着法形式目前停在离线研究；上表的训练期辅助目标只保留为**有条件的变化编码/表征研究方向**，不构成采用决策。第二份数据有单步 Q 候选覆盖，但没有完整合法变化序列。

CLM 文本骨干 Qwen3-8B 为 8.2B 参数，BF16 仅权重理论下界 `8.2e9 × 2 ≈ 16.4 GB`（约 15.27 GiB）。还要激活、KV/框架缓存、双头和现有围棋 NN；[RTX 5070 Ti 官方标准配置是 16 GB 显存](https://www.nvidia.com/en-ph/geforce/graphics-cards/50-series/rtx-5070-family/)，故不能假定它与 RustGo 原模型同卡常驻。量化、CPU 卸载或第二张卡属于另行实验，且量化后排序准确率必须重新验证。[Qwen 模型卡](https://huggingface.co/Qwen/Qwen3-8B)、[CLM 模型卡](https://huggingface.co/Contrastive-LM/CLM-v0.1-8B)

## 4. 条件式最终模型编排

建议的**正式模型目标**是「与 TF3 v17 B11 输出合同兼容的围棋主模型」；CLM 分支在训练期提供信号，不在逐叶推理期执行：

```text
训练：19路 22×19×19 + 19 全局特征
          │
          ▼
    围棋空间主干（B11/C768 量级，预训练或可训练重建）
          ├── 原 policy / value / 目差 / ownership 监督头
          └── 状态投影 d=256 ──┐
                               ├── 局面内对比/变化排序损失
    着法或变化序列编码器 d=256 ──┘   （仅训练期）

推理：同一围棋主干 → 原有全部输出；丢弃辅助分支
```

固定着法原型的最小探针：池化状态的一个 `768→256` 投影加 `362×256` 行动向量，约 `768×256 + 362×256 = 289,280` 个权重（忽略 bias/norm）。若再加每个交点的局部 `768→256` 投影，总计约 **485,888** 个权重；这一步已从原始 CLM 的单一状态向量转成更接近围棋空间 policy 的结构。这**只是可证伪的低成本对照**：若对照实验与普通 policy 辅助头没有差别，就不继续把固定着法排序当作创新。

真正有区别的研究版本把行动表示扩展为 **4–8 手合法变化序列**，使用 d=256、轻量两层序列编码器；状态投影和行动编码合计预算约 **0.5–2M 训练参数**，须实际实例化后重新计数。这个版本需要明确的真实轨迹/变化来源；当前 `.npz` 的 policy 和未来占位并不能凭空生成合法变化。候选会随局面而变，原 CLM 的大规模静态行动缓存优势也可能消失，必须实测。

推理侧的计划参数量是原生 B11 量级，**不是额外叠加 8B**；训练侧临时增加约 0.5–2M。主干若冻结且辅助头最终被丢弃，部署模型不会学到任何改进；故最终方案必须更新可部署主干/原头，或用明确的蒸馏训练把改进传入它们。仅把头训练好、文件扔掉不构成落地。

现有 `.bin.gz` 是推理权重，不是 PyTorch 训练检查点；当前仓库也无成熟的 TF3 训练、导出与新模型认证链。落实上述目标前，必须先完成训练图和导出格式的可复现桥接，并以**新模型自身**的 FP32 参考输出对拍。新权重的输出本来就不应和旧 B11 逐值相同；旧 plan、旧模型 SHA 和旧棋力结论不能移植。

## 5. 备选在线形态的边界

如果离线实验表明完整变化校验有稳定收益，才考虑一个独立根节点 verifier：状态编码器约 1–3M 参数、变化编码器约 0.5–2M、d=256，每手只排序已由搜索生成的 top-K（例如 K=8 或 16）合法变化。这个规模是**待验证的产品预算**，不是现有可运行模型。上线会改变搜索决策和协议，需要后续独立实现；必须和「把同等计算量直接加给搜索 visits」对照，否则无法证明 CLM 的净收益。
