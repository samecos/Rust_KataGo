## 1. 目标

将 KataGo（C++）中「下棋引擎」部分移植为 Rust 实现，落地到 `D:/code/Rust_KataGo`，并在本机完成 CUDA 推理后端优化：

- **硬件**：RTX 5070 Ti（Blackwell，SM 12.0 / compute capability 12.0，16 GB 显存）、AMD 9950X、64 GB 内存
- **模型**：`D:/code/b11fix.onnx`
- **棋盘**：仅 19 路标准棋盘
- **协议**：完整支持标准 GTP 指令 + KataGo 全部私有扩展指令（外部可调用面）；**另含 `katago analysis` JSON-lines 独立协议引擎与 `benchmark` 子命令**
- **CUDA 优化**：参考 `KataGomo_fork` 的优化经验，针对 SM120 调优；通过配置 JSON 声明目标 SMXX 架构集合，编译期按开关选择性编译对应后端；在关键 kernel 中引入 PTX

## 2. 调研结论（2026-08-13 实测）

### 2.1 三个仓库现状

| 仓库 | 结论 |
|---|---|
| `KataGo/` | 官方 C++ 引擎，基线 v1.17.2。下棋引擎核心（game+search+gtp+neuralnet 公共层）约 4 万行。CUDA 后端 = cuDNN（卷积/SDPA）+ cuBLAS（GEMM）+ 手写 half2 kernel（`cudahelpers.cu`），FP16 走 tensor core。**原生无法加载 .onnx**（只认 .bin.gz/.txt.gz 自研格式）。 |

| `Rust_KataGo/` | 本仓库。**已对齐：以 `KataGo-Lite/katago-rs` 为基座迁入**。 |

### 2.3 模型 `b11fix.onnx`（305 MB，已用零依赖方式解析）

- ir_version 10，opset 18，3034 节点，484 个 initializer，**75.0M 参数（FP32）**
- 模型名 `b11c768h12nbt3tflrs-fson-silu`，KataGo modelVersion **15**（**transformer 架构**：c768 trunk、h12 heads、fixscaleonenorm、silu）
- 输入：`input_spatial [B,22,19,19]`、`input_global [B,19]`（即 22 空间特征 + 19 全局特征，`has_mask=false`，19 路时无需 attention mask）
- 输出：`out_policy [B,6,362]`、`out_value [B,3]`、`out_miscvalue [B,10]`、`out_moremiscvalue [B,8]`、`out_ownership [B,1,19,19]`（v15 格式）
- 与 KataGomo_fork 优化的模型同架构同规模 → 其 SM120 优化经验可直接迁移

### 2.4 KataGomo_fork 优化盘点（可借鉴清单）

- **架构路线**：精确 19x19 / FP16 / NHWC / 固定 batch（B12/B16），四类实现：手写 CUDA kernel（half2/vec 向量化）、CUTLASS/CuTe AOT GEMM（`mma.sync` m16n8k16 FP16）、TileLang 生成 kernel、FlashAttention-4（SM120 用 FP16 QK/PV **双累加 both16**）
- **融合战术**（全部有 ABBA 实测证据）：宽 QKV 单 GEMM、FFN 双投影共享 A + SwiGLU epilogue、GEMM `beta=1` epilogue 原位残差、Q/K 融合 RoPE、RMSNorm→affine→SiLU 跨边界融合、policy 头融合、head BN 直出 FP32
- **调度/内存**：persisting-L2 access-policy window（trunk/inner 残差区）、双流拓扑（2 个 NN server 各自独占非阻塞 stream）、pinned 内存 + 专用 DMA stream + 事件握手单槽流水线、权重跨流共享
- **治理机制**：plan JSON（设备能力指纹 + 模型 SHA-256 + batch + 全部 tactic override），任何不匹配即拒绝（fail-closed，绝不静默回退）；离线 autotune（10 个有序决策组、小候选集、自然整图 ABBA 终裁）；8192 行 FP32 全 head 参考语料做正确性门（多数步骤要求 bit-identical）
- **明确否决项**（同样重要）：CUDA Graph、BF16/FP8/FP4、winograd、tcgen05、DSMEM/cluster、attention mask 处理
- **性能**：RTX 5080（SM120）官方 CUDA 1631 → plan 2836 nnEval/s（+73.9%），超 TensorRT 39.9%
- **注意**：fork 自研 kernel 里**没有内联 PTX**（靠 CUTLASS/CuTe 与内建函数）——「PTX 手写优化」是本项目相对 fork 可以更进一步的空间

### 2.5 Rust × CUDA 生态（2026-08 时效性结论）

- **cudarc 0.19.x**（crates.io 主流的 CUDA driver/runtime 绑定）：host 侧首选；支持 nvrtc 运行时编译与 build.rs 集成
- **build.rs + nvcc** 是成熟路线：`cuda_setup`、`cu-embed` 等 crate 已封装「编译 .cu → 嵌入 cubin/PTX → 运行时按架构选择加载」，正好匹配「SM 配置 JSON + 编译期选择」的需求
- **CUDA-Oxide 0.1**（NVlabs，2026-05 发布）：官方 Rust→PTX 编译器，实验性（SIMT 内核用 Rust 写）。**暂不作主线**，列为 M4 后的探索项
- **PTX 路线**（成熟稳定）：CUDA C++ 内联 PTX（`asm volatile`，官方文档）→ nvcc 编译 → cudarc 加载；可手写 `mma.sync.aligned.m16n8k16` FP16 张量核路径、向量化 load/store 等
- **SM120 硬件事实**：消费级 Blackwell（sm_120）**没有** tcgen05/wgmma/TMEM（数据中心独有）；sm_120a 有 FP4/FP8 块缩放 mma（需 `sm_120a` 目标）；fork 已验证 Ampere 风格 m16n8k16 FP16 mma 即可拿到绝大部分收益

## 3. 功能需求

- **F1 棋盘与规则**：19 路棋盘、Zobrist 哈希、气/提子/打劫（simple/positional/situational superko）、自杀判定、终局与计分、贴目、让子、encore 阶段；规则 JSON 序列化与简称解析（chinese/japanese/aga/tt/kgs 等）
- **F2 GTP 全指令**（完整清单见附录 A）：标准 GTP 全部 20+ 条；私有扩展 kata-set/get-rules、kata-set/get-param(s)、kata-list-params、kata-get-models、kata-search(_cancellable)、kata-analyze / lz-analyze / kata-genmove_analyze / lz-genmove_analyze 系列、kata-raw-nn / kata-raw-human-nn、kata-time_settings / kgs-time_settings、kata-benchmark、clear_cache、set_position、get_komi、rectangular_boardsize、kgs-rules、stop 等；输出格式逐字段对齐 `docs/GTP_Extensions.md`
- **F3 搜索**：多线程 MCTS（Search/AsyncBot）、完整 SearchParams 参数系统（运行时热改）、5 类时间控制（none/absolute/canadian/byoyomi/fischer/fischer-capped）、pondering、可取消搜索、NN 结果缓存
- **F4 模型加载与特征编码**：解析 `b11fix.onnx`（opset 18 transformer 算子集）→ 权重张量 → FP16 转换；`nninputs` 棋盘特征编码（22+19 特征、8 对称性）；v15 输出解码（policy 6×362 / value / misc / ownership）
- **F5 CUDA 后端与 SM 配置**：SM 配置 JSON 声明目标架构集（见 §5）；build.rs 按配置生成各架构 cubin/PTX；运行时按 `cudaGetDeviceProperties` 选择最优后端，不匹配 fail-closed；batch 调度与双流流水线
- **F6 PTX 优化**：关键 GEMM/卷积/attention 的 `mma.sync` FP16 张量核路径、向量化访存、融合 epilogue 内联 PTX；对齐 fork 的保序 FP32 归约纪律
- **F7 正确性门**：与 C++ KataGo 同模型同参数逐局面 NN 输出对拍（FP32 参考语料 + FP16 误差门）；GTP 指令级回归测试
- **F8 分析引擎与基准**（已纳入）：`katago analysis` JSON-lines 协议引擎（query_version/query_models/terminate/terminate_all/analyze/clear_board 等）与 `benchmark` 子命令

## 4. 非功能需求

- **N1 性能**：以 KataGomo_fork 在 SM120 的成果为参照（5080：2836 nnEval/s @ B16 双流）；5070 Ti 目标值以实测 autotune 为准，验收 = 超过官方 cuDNN 后端与 TensorRT
- **N2 正确性**：棋力与 C++ KataGo 同模型同参数一致性验证（对局胜率 / 局面输出对拍）
- **N3 可维护性**：workspace 分 crate；SM 配置与 tactic 全部配置化（JSON 驱动，不硬编码）；优化决策留痕（沿袭 fork 的 stage 记录习惯）

## 5. 架构草案

**基座（已对齐）**：workspace 中 `kata_*` crates 直接迁自 `KataGo-Lite/katago-rs`，在其 `kata_nn` 上补齐后端。

```
Rust_KataGo/
├── docs/                       # 需求、设计、优化记录
├── configs/
│   └── sm-targets.json         # SM 目标配置（编译期开关的数据源）
├── plans/                      # autotune 产物 plan JSON（每 GPU/模型/batch 一份）
├── crates/
│   ├── kata_core/kata_game/kata_search/...   # 迁自 katago-rs
│   ├── kata_nn/                # NN 接口、ONNX 解析、特征编码、NNEvaluator 批处理
│   ├── nn-backend-cuda/        # CUDA 运行时、plan 加载、调度、双流拓扑
│   ├── nn-kernels/             # .cu/.ptx 源码 + build.rs（读 sm-targets.json，调 nvcc）
│   ├── nn-backend-cpu/         # ndarray 参考后端（正确性门用）
│   └── nn-backend-trt/         # TensorRT 兜底后端（本机 TRT 10.16）
└── katago/                     # CLI：gtp / analysis / benchmark 子命令
```

`sm-targets.json` 示例：

```json
{
  "schema": 1,
  "targets": [
    {
      "id": "sm_120",
      "compute_capability": "12.0",
      "nvcc_arch": ["compute_120", "sm_120"],
      "features": ["tensor_fp16", "persisting_l2"],
      "kernels": ["gemm_m16n8k16", "flash_attn_both16", "conv3x3_im2col", "elementwise_half2"],
      "plan_hint": "plans/sm120/rtx5070ti-b16-s2.json"
    },
    {
      "id": "sm_89",
      "compute_capability": "8.9",
      "nvcc_arch": ["compute_89", "sm_89"],
      "features": ["tensor_fp16"],
      "kernels": ["gemm_m16n8k16", "elementwise_half2"]
    }
  ],
  "default_targets": ["sm_120"]
}
```

编译/运行机制：build.rs 读 JSON → 生成 cargo cfg（如 `--cfg target_sm_120`）+ nvcc `-gencode` 参数 → 各架构 fat binary 随程序分发 → 运行时探测设备 capability，在编译入的集合中选最优，plan 指纹校验不通过即报错（fail-closed）。

**后端路线（已对齐）**：手写 CUDA C++/PTX kernel 为主线（nvcc 编译、cudarc 加载），TensorRT 10.16 作功能兜底，逐算子替换直至全手写。

## 6. 里程碑（建议）

- **M1 基座整合**：katago-rs 迁入 Rust_KataGo；cargo build/test 全绿；GTP 骨架跑通（dummy NN）
- **M2 推理打通**：ONNX 解析 + 权重 FP16 转换；CPU 参考后端；与 C++ KataGo 同局面 FP32 对拍建正确性门
- **M3 CUDA 第一版**：nvcc 编译 .cu（GEMM/3x3 卷积/attention/elementwise，FP16 + mma）→ cudarc 加载跑通；性能达到官方 cuDNN 后端量级
- **M4 SM120 专项**：逐项落地 fork 战术清单（宽 QKV、融合 FFN、FA both16、persisting L2、双流、plan 机制）+ PTX 手写关键 kernel；离线 autotune；性能对标验收
- **M5 兼容与验收**：GTP 全指令回归、analysis/benchmark、与 C++ KataGo 棋力一致性验证

## 7. 风险

1. `katago-rs` 的 `kata_nn` 尚在开发中（eval/后端接口 wip），需先补齐接口层（其 `doc/rust-port-plan.md` 已有路线图）
2. b11fix.onnx 算子集需逐一实现/映射（opset 18 transformer：conv/BN/GEMM/softmax/RMSNorm/RoPE/SwiGLU 等），无官方 ONNX 加载路径可抄
3. FP16 精度纪律：需复刻 fork 的保序 FP32 归约与正确性门，否则棋力漂移
4. Windows + nvcc + build.rs 工具链（需 cl.exe 与 nvcc 在 PATH；已有 cuda_setup/cu-embed 成熟方案）
5. fork 的 autotune 结论基于 5080/4090D；5070 Ti（16 GB、规格更低）需重新 autotune，不可直接套用其 plan
6. CUDA-Oxide 0.1 为实验性编译器，主线仍用 nvcc + CUDA C++/内联 PTX，风险可控
7. 本机无系统 cuDNN：官方后端路径不可直接复用；手写全部算子或从 PyPI wheel 提取 cuDNN DLL（fork 做法）二选一
