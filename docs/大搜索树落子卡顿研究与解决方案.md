# 大搜索树落子卡顿：定位、实验与可移植方案

2026-09-20。本轮任务是研究大搜索树下切换局面的停顿，形成单机 RustGo 与 Go Server 都能采用的解决方案。模型范围为原版 b11 和剪枝版 b15。**本轮完成源码定位与隔离原型实验，尚未发布可替换使用的优化引擎。**

## 结论

落子不是只有修改棋盘这一步。当前实现把停止搜索后的缓存写回、子树标记、孤儿节点释放，以及下一轮搜索的统计重算串在交互路径中。这些工作随图规模增长；有些遍历还会重复访问共享节点。即使没有 GPU、Worker 和网络，也能复现停顿。

建议先实施 **图遍历去重 + 保留子树的正确剪枝 + 有界异步析构**。保持搜索统计和模型计算，先把大批内存释放从落子关键路径移走。随后根据阶段计时处理统计重算和剩余的全图扫描。Server 可复用回收协议与验收方法，但不能直接套用 RustGo 的裸指针容器实现。

隔离原型中，30 万节点、落子保留约 10% 时，RustGo 标记和回收的前台时间由约 **189 ms 降到 17 ms**。这证明延后析构值得实施；它不是已交付版本的端到端成绩，也不表示消除了所有规模下的停顿。

## 2. 单机 RustGo 的阻塞链

```text
GUI/GTP 收到落子
  → 停止分析 / AsyncBot::stop_and_wait
  → 等搜索线程结束（包括末尾评估缓存写回）
  → make_move_with_prevent
      → 克隆选中子节点作为新根（不是深拷贝整棵树）
      → 遍历保留子图，标记可达节点
      → 扫描节点表，撤回 bias 贡献并析构旧节点
  → 启动下一轮 begin_search
      → 可能重算保留子图全部统计
      → 清理旧 NN 输出与未使用 bias 表项
  → 开始新的搜索 / 输出分析
```

定位到的代码：

| 阶段 | 位置 | 发现 |
|---|---|---|
| 等待停止 | `crates/kata_search/src/async_bot.rs::stop_and_wait`、`search_thread_loop` | 发停止标志后仍等待 `run_whole_search_full` 完整返回和分析回调结束 |
| 缓存写回 | `search.rs::recursively_record_eval_cache` | 普通递归沿所有边访问，**没有节点去重或环检测**；即便节点未达到缓存门槛，也先递归子图 |
| 换根 | `search.rs::make_move_with_prevent` | 保留可达子树后同步清理整张节点表 |
| 释放旧节点 | `delete_all_old_or_all_new_table_nodes_and_subtree_value_bias_multithreaded`、`delete_all_table_nodes_multithreaded` | 名称带 multithreaded，实际都是单线程遍历和析构；前者还先收集 key 再二次查表删除 |
| 下一轮初始化 | `search.rs::begin_search`、`recursively_recompute_stats` | 动态目差效用、subtree bias 或 pattern bonus 启用时遍历保留图重算；当前实现使用串行显式栈 |
| 附属清理 | `subtree_bias.rs::clear_unused_synchronous` | 同步扫描 bias 表；NN 旧输出也同步析构 |

CLI 默认 `dynamicScoreUtilityFactor=0.3`、`subtreeValueBiasFactor=0.45`，与 `SearchParams::new()` 的零值不同，测试必须区分。`useEvalCache` 的代码默认关闭，但 `configs/gtp_cuda.cfg` 显式开启。因此缓存问题是配置相关的额外放大因素，不能用它解释全部卡顿。

本机 C++ KataGo 源码的缓存记录使用带去重的多线程后序图遍历，节点删除也实际分片并行。Rust 的两处实现未保留这些性质。Rust 标准库另明确说明，HashMap 的遍历按 **capacity** 而非仅 len 计费，因此经历过大树后，低填充率表也有扫描成本。[Rust HashMap 文档](https://doc.rust-lang.org/std/collections/struct.HashMap.html#method.iter)

还有两类固定或外部等待需要分开记账：尚未结束的 NN 批次/回调，以及 GTP 首帧尚未输出时最多 1 秒的等待逻辑。后者不随树规模增长，不是本次大树回收问题的充分解释。

## 3. 已完成的离线实验

所有计时为 release 模式、源码副本、CPU 本地实验。未使用真实模型加速结果作为依据，未连接或操作生产会话。机器上的现有服务仍在运行，样本少且部分波动明显，**不能作为正式 ABBA 收益门通过的声明**。

### 3.1 单机标记与释放

合成图使用真实 `SearchNode`、节点表、NNOutput/ownership 分配和当前图遍历/删除方法，覆盖 1 万、10 万、30 万节点以及 10%/90% 保留比例。每组按 ABBA 顺序运行，两次 A 与两次 B。

仅做分片并行释放能改善耗时，但仍会阻塞。单线程“先标记再入栈”原型在大保留子图上反而慢于原有多线程标记，不能整体直接替换现有遍历。

进一步把删除拆成“前台摘除并取得节点所有权”与“随后析构”，第一次完整实验的均值如下：

| 原图节点数 | 保留比例 | 原同步标记+删除 | 延后析构的前台部分 |
|---:|---:|---:|---:|
| 100,000 | 10% | 62.13 ms | 6.61 ms |
| 100,000 | 90% | 11.40 ms | 5.76 ms |
| 300,000 | 10% | 188.75 ms | 16.60 ms |
| 300,000 | 90% | 43.59 ms | 13.83 ms |

原型保持当前多线程标记；前台从表中移除不可达节点并收集 `Box<SearchNode>`，析构时间单列。**它没有运行一个与新搜索竞争资源的后台回收线程**；因此这里只测出了可从前台迁走的工作量。30 万/10% 场景延后的析构仍花费约 184～228 ms，正式版本必须测后台争用与内存峰值。

随后加入保留 key 集合、保留边指向存活节点、访问统计不变的断言，重新运行四组 ABBA 验证，16 个样本全部通过。复验中 30 万/10% 的前台均值为 188.34 → 11.80 ms，30 万/90% 为 37.99 → 11.74 ms。不同轮次有明显波动，本文不把其中最快一轮当正式加速成绩。结果见 `probe-retirement-verified.log`、`retirement-verified.json`。这不是所有搜索语义的等价证明，特别是并发、bias 撤回和真实共享图仍需正式回归。

### 3.2 共享节点的重复缓存遍历

构造分层菱形 DAG：每层两个节点，每个父节点连接下一层的两个节点。28 层只有 **57 个唯一节点**，原方法却会执行 **536,870,911 次递归调用**。两次原始测量约 **2.42 / 2.47 秒**；按地址去重的原型约 **0.015 / 0.008 ms**。

这个极端合成图说明原算法工作量可随路径数量膨胀，不代表实际围棋局面的共享程度。此测试把访问数设在缓存门槛以下，专门隔离遍历开销，不能替代有效缓存内容的等价验证。有环时原方法还缺少终止保证；没有执行会导致无限递归的基线实验。

### 3.3 实际搜索代码生成的树

CPU dummy evaluator、19 路、8 线程、50,000 visits 上限；动态目差效用和 bias 因子按 CLI 默认开启。实际生成 38,915 个表节点：

- 停止后的全图缓存记录：5.30 ms。
- 同一大根重新 `begin_search`：14.97 ms。
- 选中落子后 `make_move`：19.74 ms，剩余 124 个表节点。
- 小子树下一轮 `begin_search`：0.99 ms。

这是一次诊断样本，验证多个独立阶段都存在耗时；dummy 的分支分布不是 b11/b15 的真实分布，也没有测从 GUI 点击到下一条分析输出的延迟。

### 3.4 Server 源码副本

`D:/Go/Server/crates/go-core/src/search.rs::set_root → collect_unreachable` 同步执行：可达遍历、扫描旧 Vec、丢弃旧节点、建立 old→new 映射、改写保留节点的边、重建全部 parents 和 index。会话 actor 要等此过程结束才返回新的权威快照。

合成图每节点 256 个候选边槽，包含共享子节点和环，使用当前真实 Node/Edge 类型。A 为当前方法，B 仅将稠密节点编号对应的 HashSet/HashMap 换成数组。

| 节点数 | 保留比例 | 原方法 | 数组原型 |
|---:|---:|---:|---:|
| 100,000 | 10% | 143.09 ms | 136.90 ms |
| 100,000 | 90% | 190.16 ms | 162.38 ms |
| 300,000 | 10% | 566.46 ms | 486.34 ms |
| 300,000 | 90% | 605.04 ms | 485.23 ms |

24 个样本全部通过图内容摘要一致性检查，覆盖节点 key/统计、子边及顺序、parents、index、ownership。1 万节点/10% 场景数组原型反而略慢，故没有将它应用到 Server。只换容器仍是全图搬迁，不能作为消除卡顿的最终方案。

## 4. 建议实施顺序

### 第一步：补齐计时和图遍历正确性

在独立的新引擎中按单次命令/搜索代记录：停止请求到 playout 退出、缓存写回、分析回调等待、保留标记、bias 撤回、摘除、实际析构、统计重算、bias 表清理、新根首次 NN 请求和首条新分析。

缓存遍历改为每个节点至多处理一次，显式处理环。先保持原有缓存更新门槛、root 特例和快照语义，核对缓存内容；不把关闭 `useEvalCache` 当正式修复。

### 第二步：RustGo 分离逻辑剪枝与物理释放

落子时仍先等搜索与回调达到安全点。保留现有子树统计和必要可达性判定，然后：

1. 从活动节点表中移除不可达节点，撤回应撤回的 subtree bias 贡献。
2. 转移节点、旧根和可延后的 NN 输出的唯一所有权，形成 `RetiredBatch`。
3. 发布新根并继续运行；由专用回收器分批 drop 已摘除对象。
4. 回收器只处理自己拥有的对象，不遍历活动搜索图，不持活动表锁执行大批析构。

必须在对象析构前明确撤回 bias，处理其 Arc 引用对 `clear_unused_synchronous` 的影响。不能简单把整个 `clear_search()` 放进另一个线程：Search 和保留子图仍有共享裸指针，会产生生命周期和并发风险。

回收队列必须有节点数/估算字节预算，且计入“活动树 + 待回收对象 + 临时工作区”的总内存。连续落子、悔棋、清盘时通过暂停新搜索分配和增加回收配额追赶，不让队列无限增长。关闭进程时统一 join 回收线程；普通落子不 join。

这一步仍有全表扫描和保留标记，复杂度仍随树规模增长，不能承诺任意大树严格固定延迟。先用真实局面检查它能否达到交互目标，再决定是否进入更大的容器改造。

### 第三步：覆盖“新一轮开始前”的停顿

缓存去重和延后析构之后，继续单列检查 `recursively_recompute_stats`。保持原计算顺序依赖，优先恢复可并行的后序工作，并在效用上下文确实未变、节点也未脏时跳过不必要的重算。

动态目差中心、bias、pattern bonus 发生变化时不能无条件复用旧 utility。若引入按代懒更新或增量缓存，必须设计失效传播、共享节点更新与快照边界；不能把全树递归原样挪到首次选点处，那仍会阻塞第一条新分析。此部分尚未实现或测出加速结果。

### 第四步：Server 移植及更大规模结构

Server 首阶段可采用同样的“先正确摘除，再延后析构”，复用相同延迟指标与内存预算协议。与 RustGo 的重要区别是它目前使用密集 Vec 下标：落子会重编号，因此不能在旧编号仍被使用时直接异步搬迁。

若重映射/父索引重建仍占主要成本，后续改为稳定节点槽和带槽代数的 NodeId，节点释放后进入 free list，换根不重排所有活节点。反向 parents 要支持失效链接清理，内存记账必须区分 live、retired、空槽和容器 capacity。

进一步的增量 GC 才能把剩余的全图工作切成有限时间片。它需要满足以下协议，不能仅把现有扫描循环拆开：

- 换根前撤销旧 EvalToken/虚拟占用并增加搜索代，迟到结果不能写入新树。
- GC 标记有自己的 epoch；再落子必须取消或重启未完成的回收轮次。
- 搜索期间新连接的共享子节点必须有写屏障/染色规则，不能回收刚被重新连入的节点。
- 清理反向 parent 链接与节点表后才能复用槽位；旧 NodeId 不能命中新槽。
- 如果还没有上述并发协议，则回收只在搜索安全点进行；不能声称并发扫描已经安全。

RustGo 与 Server 的公共层宜是回收批次所有权、队列预算、epoch/安全点约定及遥测；图存储适配分别实现。单纯引用计数也不足以处理搜索图中的环。

## 5. 同一个新程序支持 b11 / b15

当前工作区的原生模型解析和 CUDA 层图已包含 b11 与剪枝 b15 的结构支持，既有验证见 `RustGo剪枝模型支持.md`。本轮拟改搜索生命周期，不分叉模型后端，不引入模型专用搜索版本。

正式实现时使用新输出目录，例如：

```powershell
cargo build -p katago --features cuda --release --target-dir target/move-latency-v1
```

交付一个新 `katago-rs.exe`，按加载模型识别结构；测试 b11 和 b15 的 GTP/analysis/nnworker 入口，不要求换另一份可执行文件。模型文件及其匹配 PLAN 仍是不同身份，不能伪造指纹把两模型并入一份认证计划。是否能使用已有 PLAN，应由新程序实际 fingerprint 和既有 fail-closed 规则判定。

本文中的两个测试可执行文件只是 CPU 研究探针，不是这个未来的可用 CUDA 引擎。

## 6. 验收口径

建议目标是：预热后，在约定的 10 万、30 万、100 万节点测试集上，**引擎落子确认 p95 < 50 ms、p99 < 100 ms**；这是待验证目标，不是本轮已达成指标。首条新分析另记时间，扣分项包括启动阶段的大树停顿，不能只看 `play` 返回。

覆盖主分支/冷门落子、不同保留比例、pass、悔棋、清盘、改 komi、快速连续换根、共享图及有环图。分别开启/关闭 eval cache，记录节点数而非仅 visits。

正确性验证必须包括：保留节点和边、统计、bias 撤回、缓存内容、旧 NN 结果作废、虚拟占用归零、队列完全清空、退出与长期 RSS。保持 NN 计算未变；双模型真实推理与数值验证复用既有门。

性能验收分别对 b11、b15 在相同模型/配置/局面下运行 ABBA，比较搜索吞吐、端到端延迟分布、回收积压和内存峰值。后台回收会竞争 CPU/分配器，不能只报告前台缩短而忽略搜索减速。研究原型尚未通过这一发布门。
