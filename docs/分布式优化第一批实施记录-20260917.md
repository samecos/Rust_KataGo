## 实现与使用

源码入口：

- [main.rs](D:/Go/Server/crates/go-server/src/main.rs)：使用 `TcpIncoming::from(listener).with_nodelay(Some(true))`，锁定 tonic 0.14.6 本地实现已核实；新增 CLI 参数。
- [worker.rs](D:/Go/Server/crates/go-server/src/worker.rs)：独立派发预算、物理信用、连接内观测、发送通道取出计时和 actor 邮箱计时。
- [worker_schedule.rs](D:/Go/Server/crates/go-server/src/worker_schedule.rs)：按派发时在途数量分档的 RPC 完成时间估计、启动探测、供料充分时的完成率估计。completion 的评分不使用硬容量作为算力权重。
- [worker_metrics.rs](D:/Go/Server/crates/go-server/src/worker_metrics.rs)：固定2048条最近样本窗口、精确 nearest-rank p50/p95/p99、累计消息字节。
- [JSON 字段契约](D:/Go/Server/docs/json_api_v1.md)：新增字段、采样边界和不能推导的指标。

构建：

```powershell
cd D:/Go/Server
cargo build --release -p go-server
```

默认运行启用连接修正和观测，保持 legacy 调度。实验调度在原 Server 启动参数上增加：

```text
--worker-scheduler completion --worker-target-inflight 64
```

按 Worker 分别配置目标窗口：

```text
--worker-scheduler completion --worker-target worker-a=32 --worker-target worker-b=64
```

目标必须为1..4096，实际值裁剪到 Hello 硬容量。legacy 未配置目标时使用原硬容量；completion 未配置时使用 min(64, capacity)。新连接先给最多4个探测信用，取得4个成功回包后开放配置目标。重连重置性能估计。

目标为所有会话共享。completion 对正在等待派发的会话轮转；取消立即移除等待者，失活等待者20ms到期。取消中的任务继续占用物理信用，终态回包或连接 epoch 回收后才释放。旧连接和重复回包不能释放新任务信用。

此版窗口为显式配置值；自动扩缩窗、deadline 感知、应用层探针仍待后续实施与验证，未包装成已完成能力。

## 观测的实际含义

`/api/workers` 和快照新增 `targetInFlight`、`dispatchLimit`、`scheduler`、`predictedCompletionMs`、`suppliedThroughputRps`、同会话/跨会话在途背景下的派发次数与 `metrics`。`/health.configuration.workerScheduling` 可读回启动配置。

消息长度统计外层 protobuf 加5字节 gRPC 头，不是网卡抓包流量。请求分别记录成功入队和 tonic 拉取；发送排队只覆盖这两点之间，不包含之后的 HTTP/2 流控。结果统计当前连接收到的全部回包，包括错误、重复与退休；RPC 分布仅记录匹配到唯一待办任务的终态回包。

阶段分布为最近2048条，`totalCount` 为累计样本数，`windowCount` 为当前分位数样本数。可选阶段缺失不填0，EWMA 字段继续保留。不能相减不同阶段的 p95，不能通过前后窗口分位数相减构造单个实验的 p95。

现有 v1 只有 NN rows/batches 累计数，尚不能提供逐批大小分布、逐请求缓存命中或精确取消尾部 NN rows。验收继续使用前后排空及新心跳确认总量，保留 retiredResults。模型执行时间包含 evaluator 等待，不等于 GPU kernel 时间。

搜索测量工具新增 `--expected-engines`，显式固定各 Worker 的 engineCommit，支持 RustGo 的功能/吞吐测量；默认仍要求原固定 KataGo 基座。非该基座不能冒用 v1 正式质量参考。样本中目标窗口、调度器或连接变化会被拒绝。

## 本机有限验证

### 功能与生命周期

最终验证：`cargo test --workspace` 为69通过、0失败、5个既有显式忽略项；搜索测量契约8项 Python 测试通过；`cargo fmt --all -- --check` 与 `git diff --check` 通过。completion 模式另外使用同一真实 CUDA Worker 完成7/60/260手的预热、1秒与8秒分析，共9个样本，失败计数均0，目标64与实际 scheduler 读回一致。该组只作功能冒烟，不作调度性能对照。

Server 工作区测试覆盖原有取消、租约、断流、模型身份、非法上下文、friendly pass、搜索图预算和多会话流程。新增检查包括：

- accepted socket 实际读取到 NODELAY=true。
- capacity1024 与64在相同窗口下均获得启动探测，不因硬容量获得16倍性能评分；测得速度不同会影响后续分配。
- 目标裁剪、参数拒绝、等待会话下一信用、公平分配、取消保留物理信用、重复回包和旧连接隔离。
- 编码字节与真实序列化一致，缺失阶段不补零，actor 取出时才记录等待时间，窗口容量有界。
- 两个合成 Worker（硬容量1024/64、目标均2）服务两个真实网络会话，均完成 genmove；这是生命周期测试，不是双 GPU 性能数据。

两份 proto 的 SHA256 仍为 `8a43d78331e64040f44e2c0fe49456d6d75c9ea88b11b111e03473fb48741e5e`。没有 GPU 数值变更，本轮不重复已结项的 kernel 实验或整图数值优化。

### 默认路径的 ABBA

A 是改动前 Server，B 是本轮 Server 的默认 legacy 路径；**不是 C++/Rust 引擎对比**。同一 RustGo 二进制、TF3模型、B14/S2/C64认证配置；AMD Ryzen 9 9950X、单张 RTX5070Ti、驱动610.88，Windows IPv4 回环，独立端口18090/15051。

每个进程组重启 Worker，固定7/60/260手局面顺序，每局面1秒预热，随后1秒短分析及8秒持续分析。缓存启用并保留至该组结束；fresh graph 不代表冷缓存。所有阶段前后检查物理排空与新心跳。图上限128，发布100ms，图内存1GiB仅用于隔离实验。

预登记门：有效完成评估数改善至少5%，非主指标退化不超过3%，同侧两次样本相对跨度不超过5%。没有棋力/参考质量通过结论，首结果受100ms快照粒度限制，不从两次样本伪造首结果 p95。

1. 首次尝试使用512MiB，A1的260手持续分析在约7.818秒触及图内存上限（536,776,489逻辑字节），在运行候选前停止。原始失败轨迹保留。第二次重新预登记，两侧统一1GiB后完成，不把失败样本当成成功。
2. 第二次 A1 的60手持续分析与一次本地 Rust 网络测试编译重叠：分析开始01:42:32 UTC，测试二进制完成写入01:42:39.575 UTC。这会影响 CPU 负载；该样本仍保留，不能作为严格隔离的性能认证。
3. 本机只有一张实际参与测量的 GPU，没有 LAN/WAN、双 GPU 混合池或正式搜索质量参考。调度完成顺序变化也不能直接解释成棋力变化。

B2的260手8秒样本可核查观测：派发14303、有效回包14256、退休回包47、NN rows10838、batches793；请求编码28,209,522字节、回包编码24,245,302字节。该阶段末尾最近2048条中，RPC p95=56.769ms，发送队列 p95=0.0189ms，actor 等待 p95=1.2776ms，context p95=0.093ms。这里只说明字段工作正常，不与旧版不存在的分位数字段作虚假对比。
