# Rust_KataGo 编译指南：从源码到 katago-rs 可执行文件

> 2026-08-25。面向想在自己机器上编译出二进制的玩家。当前共三个可用后端：
> `dummybackend`（默认，无 GPU）、`cudabackend`（手写 CUDA kernel，主线）、
> `trtbackend`（TensorRT 兜底）。
> 命令分 PowerShell（Windows 原生）和 bash（Linux / WSL2）两套，路径按本机替换。
> 产物统一是 `target/release/katago-rs.exe`（Windows）或 `target/release/katago-rs`（Linux/WSL）。

## 0. 结论速览

| 后端     | 编译命令（release）                               | 额外依赖                                                       | 编译时需要 GPU？ |
| -------- | ------------------------------------------------- | -------------------------------------------------------------- | ---------------- |
| dummy    | `cargo build --release`                           | 无（只要 Rust 工具链）                                         | 否               |
| CUDA     | `cargo build -p katago --features cuda --release` | CUDA Toolkit（含 nvcc）+ 宿主 C++ 编译器；CUTLASS 可选（推荐） | 否               |
| TensorRT | `cargo build -p katago --features trt --release`  | CUDA Toolkit + TensorRT 10.x + 宿主 C++ 编译器                 | 否               |

- 编译全程不需要 GPU，GPU 只在**运行**真实推理时需要；dummy 后端连运行都不需要。
- 编译不需要安装 protoc（build.rs 使用 vendored 副本）。
- 后端在运行时用配置键 `nnBackend` 选择（`dummybackend` / `cudabackend` / `trtbackend`），
  编译期由 cargo feature 决定哪些后端被编进二进制。
- `cuda` 和 `trt` 是两个独立 feature，按需只开其一即可；Cargo 层面允许同时启用，
  但 TRT 侧仍受 §4 的 TensorRT 10.x 版本约束。

## 1. 公共准备（所有平台、所有后端）

1. Rust stable，`rustc >= 1.85`（项目使用 edition 2024）：

   ```bash
   # Linux / WSL（Windows 用 rustup-init.exe，默认选项即可）
   curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh -s -- -y --default-toolchain stable
   ```

2. 获取源码：

   ```bash
   git clone https://github.com/samecos/Rust_KataGo.git
   cd Rust_KataGo
   ```

3. 真实推理需要模型文件（dummy 冒烟测试可用 `/dev/null` 占位），见 §7。

### 1.1 Windows 公共：Visual Studio 生成工具

Windows 上无论编哪个后端，都需要 **Visual Studio 2022 生成工具 + "使用 C++ 的桌面开发" 工作负载**
（Rust 的 MSVC 目标需要 link.exe；`cuda`/`trt` feature 还需要 cl.exe 作为 nvcc / C++ shim 的宿主编译器）。

- 安装后**不需要**手动进 Developer Command Prompt 或 vcvars：build.rs 通过 cc crate 自动探测 cl.exe。
- Rust 默认 host triple 是 `x86_64-pc-windows-msvc`，与上述工具匹配；不要切换到 GNU 工具链。

### 1.2 Linux 公共：基础包

```bash
sudo apt-get update
sudo apt-get install -y curl build-essential pkg-config libssl-dev ca-certificates
```

`libssl-dev` + `pkg-config` 是 workspace 里 reqwest 默认 TLS（OpenSSL）需要的；
`build-essential` 提供 gcc/g++（CUDA 与 TRT 的宿主编译器）。

## 2. 后端 A：dummy（默认，先跑通）

不编任何 feature，不需要 CUDA/TensorRT，任何平台（含无 GPU 的机器、CI）可编译：

```powershell
# PowerShell
cargo build --release
```

冒烟验证（`/dev/null` 是 dummy 模型的哨兵值，Windows 上也照写）：

```powershell
"protocol_version`nname`nboardsize 19`nclear_board`nkomi 7.5`ngenmove B`nquit`n" |
  .\target\release\katago-rs.exe gtp --config .\configs\gtp_smoke.cfg --model /dev/null
```

```bash
# bash（Linux / WSL；也可用于 Windows 的 Git Bash）
cargo build --release
KATAGO_MODEL=/dev/null scripts/gtp_smoke.sh
```

能打印 GTP 应答（protocol_version=2、genmove 返回坐标）即编译成功。
dummy 后端不做真实神经网络评估，只验证棋盘/搜索/GTP 链路。

`cargo test --workspace` 也可全量跑通（不需要模型和 GPU）。

## 3. 后端 B：CUDA（主线）

### 3.1 安装 CUDA Toolkit

从 NVIDIA 官网安装与本机 GPU 匹配的 CUDA Toolkit（编译期只要 toolkit，不需要装好驱动）：

| GPU（示例）             | 计算能力       | toolkit 最低版本 | 默认 `configs/sm-targets.json` 是否覆盖 |
| ----------------------- | -------------- | ---------------- | --------------------------------------- |
| RTX 50 系（如 5070 Ti） | 12.0（sm_120） | CUDA 12.8        | 是                                      |
| RTX 40 系               | 8.9（sm_89）   | CUDA 11.8        | 是                                      |
| RTX 30 系               | 8.6（sm_86）   | CUDA 11.7        | **否，需自己加，见 3.2**                |
| RTX 20 系               | 7.5（sm_75）   | CUDA 10          | **否，需自己加**                        |

装好后在终端确认 nvcc 可用：

```powershell
nvcc --version        # 或 & "C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.8\bin\nvcc.exe" --version
```

```bash
/usr/local/cuda/bin/nvcc --version   # Linux 默认装在这里，可能不在 PATH
```

build.rs 定位 nvcc 的顺序：环境变量 `CUDA_PATH`（Windows 安装器默认会设置）/
`CUDA_HOME` 指向的 `bin/nvcc[.exe]` → 直接搜 `PATH`。找不到时**构建不报错**，只打
`cargo:warning=nvcc not found — CUDA kernels not compiled`，后果是运行时报
`no compiled SM target compatible with device capability X.Y`。遇到这个错误先查 nvcc。

### 3.2 按你的 GPU 配置 sm-targets.json（老卡必读）

`configs/sm-targets.json` 列出要为哪些架构编译 PTX（默认 `sm_120` + `sm_89`，
在仓库里都已包含）。运行时选择规则：

1. 先找与设备计算能力**精确相等**的目标；
2. 否则选**数值上不大于**设备能力的最高目标（PTX 由驱动 JIT 前向兼容）；
3. 都没有 → 启动报错。

因此 RTX 30/20 系等较老的卡必须把自己的架构加进 `targets` 数组，例如 RTX 3060（sm_86）：

```json
{
  "id": "sm_86",
  "compute_capability": "8.6",
  "nvcc_ptx_arch": "compute_86",
  "nvcc_cubin_arch": "sm_86",
  "features": ["tensor_fp16"]
}
```

（PTX 编译只读 `id` / `compute_capability` / `nvcc_ptx_arch` 三个字段，其余是描述性的。）

两个可接受的现象，不用修：

- toolkit 太老、编不了 `sm_120` 时，该目标会被跳过（warning：
  `SM target sm_120 omitted because one or more kernels failed to compile`），其余目标照常用；
- 每个 `.cu` 是编成 PTX 嵌入二进制的，首次运行新架构会有一次驱动 JIT（有缓存，之后不再发生）。

### 3.3 编译与产物

```powershell
cargo build -p katago --features cuda --release
```

```bash
cargo build -p katago --features cuda --release
```

首次编译较慢（每个 kernel × 每个 SM 目标各跑一次 nvcc，再叠 thin-LTO），属正常。

### 3.4 可选但强烈推荐：CUTLASS（DualFFN tactic，实测 +26% 推理吞吐）

克隆 CUTLASS **3.9.2**（验证过的版本）到仓库内约定位置，或任意位置后设环境变量：

```bash
# 方式一：仓库内（无需环境变量，build.rs 自动发现）
git clone --branch v3.9.2 --depth 1 https://github.com/NVIDIA/cutlass.git third_party/cutlass
```

```powershell
# 方式二：任意位置 + 环境变量（PowerShell）
$env:KATAGO_CUTLASS_ROOT = "D:\code\cutlass"
```

查找顺序：`KATAGO_CUTLASS_ROOT` → `third_party/cutlass` → 硬编码的 `D:/code/cutlass`。
目录里需有 `include/cutlass/cutlass.h` 和 `examples/45_dual_gemm/`（官方仓库克隆即有）。

找不到 CUTLASS 时**静默跳过、构建照常成功**（warning：`CUTLASS not found — dual_ffn skipped`），
代价是 `KATAGO_CUDA_DUALFFN` tactic 不可用、推理明显变慢。想确认编进去了，看构建输出里
**没有**这条 warning 即可。

注意：CUTLASS 在位但 `cuda-host/dual_ffn_cutlass.cu` 编译失败会让**构建直接失败**（fail-loud，
防止坏代码静默回退）。确实需要临时绕过时设 `KATAGO_ALLOW_BROKEN_CUDA_HOST=1`（会失去 DualFFN）。

### 3.5 验证

```bash
# CUDA 后端冒烟测试：合成数据，不需要模型文件；运行时需要 GPU（没有则自动跳过）
cargo test -p kata_nn --test test_cuda --features cuda
```

有真实模型后（§7）再做运行验证：

```powershell
.\target\release\katago-rs.exe cuda-fingerprint --model D:\models\b11fix.onnx
# 应打印 GPU/模型/构建指纹；CUDA_COMPILED_SMS 应包含你的架构

.\target\release\katago-rs.exe gtp `
  --config .\configs\gtp_smoke.cfg `
  --model D:\models\b11fix.onnx `
  --override-config nnBackend=cudabackend,nnMaxBatchSize=16
```

数值正确性对拍（可选，改动 kernel 或怀疑结果不对时用）见 README「CUDA smoke 和整图对拍」一节。

重要：`configs/gtp_cuda.cfg` 里带一条写死的
`cudaTacticPlan = D:/code/Rust_KataGo/plans/best-tactic-plan.json`（认证调优 plan）。
plan 是 fail-closed 的：GPU、模型、CUTLASS、平台任一不匹配就直接启动失败。
**在新机器上请先删除或注释这一行**（退回代码内置默认 tactic，完全可用），
需要榨性能时再自己跑 `python scripts/autotune.py` 重新认证。

### 3.6 运行环境要求

- 目标机需要 NVIDIA 显卡 + 驱动，驱动版本需支持所用的 CUDA（CUDA 12.8 → 570+，CUDA 13.x → 580+）；
- `cudart` 是静态链接的，不需要目标机装 CUDA Toolkit；
- 驱动 API（nvcuda.dll / libcuda.so）由 cudarc 在运行时动态加载，随显卡驱动提供。

## 4. 后端 C：TensorRT（兜底）

TensorRT 后端把模型在进程内转成 ONNX 再交给 TRT 推理。构建期**不需要 nvcc**，
但需要 CUDA Toolkit 的头文件/库 + TensorRT 10.x 的头文件/库。
TRT 库需要从 NVIDIA 官网下载（TensorRT 10.x，与 CUDA 版本对应的包，需免费注册账号）。

> **版本硬约束：只支持 TensorRT 10.x。** shim（`cpp-shim/src/trt_shim.cpp`）用的是
> TRT 10 时代的 API；TRT 11 的头文件已删除 `IBuilder::platformHasFastFp16`、
> `BuilderFlag::kFP16`、`kEXPLICIT_BATCH` 等接口，会直接编译失败（实测 TRT 11.2 头文件：
> `error C2039: 'platformHasFastFp16': is not a member of 'nvinfer1::IBuilder'`）。
> 注意别把新版 CUDA 自带/并入的 TRT 11 当作可用版本。

### 4.1 关键：目录布局（TRT 要"并进" CUDA 目录）

build.rs 通过 `CUDA_PATH`（或 Windows 默认安装目录 / Linux `/usr/local/cuda`、`/opt/cuda`）
找到 CUDA 根目录，然后**在同一目录里**找 TRT：

| 文件                      | 要求的位置                                                      |
| ------------------------- | --------------------------------------------------------------- |
| `NvInfer.h` 等 TRT 头文件 | `<CUDA 根>/include/`                                            |
| TRT 库（Windows）         | `<CUDA 根>/lib/x64/`（`nvinfer_10.lib`、`nvonnxparser_10.lib`） |
| TRT 库（Linux）           | `<CUDA 根>/lib/`（`libnvinfer.so`、`libnvonnxparser.so`）       |

也就是说需要把 TRT 包里的头文件和库**拷贝进 CUDA 安装目录**（这是项目验证过的布局）。
链接名硬编码为 TRT 10 的带主版本后缀形式（Windows `nvinfer_10`，Linux `nvinfer`），
所以**只支持 TensorRT 10.x**；TRT 8/9 会链接失败。

找不到 TRT 时构建**不会失败**，只打 warning（`NvInfer.h not found — TensorRT shim skipped`），
此时 `trtbackend` 会在运行时报编译期未启用。

### 4.2 Windows 步骤

1. 安装 CUDA Toolkit（同 §3.1，安装器会设好 `CUDA_PATH`）。
2. 下载 TensorRT 10.x 的 Windows zip 包并解压。
3. 合并进 CUDA 目录（版本号按实际替换）：

   ```powershell
   $trt  = "D:\TensorRT-10.x.x"        # 解压出的目录
   $cuda = $env:CUDA_PATH              # 例如 C:\Program Files\NVIDIA GPU Computing Toolkit\CUDA\v12.8
   Copy-Item "$trt\include\*" "$cuda\include\" -Force
   Copy-Item "$trt\lib\nvinfer_10.lib","$trt\lib\nvonnxparser_10.lib" "$cuda\lib\x64\" -Force
   # 运行期 DLL：放进 <CUDA>\bin（CUDA 安装器已把它加入 PATH）
   Copy-Item "$trt\lib\nvinfer_10.dll","$trt\lib\nvonnxparser_10.dll" "$cuda\bin\" -Force
   ```

4. 编译：

   ```powershell
   cargo build -p katago --features trt --release
   ```

### 4.3 Linux 步骤

推荐 tarball 方式（deb 包把头/库装到 `/usr/include/x86_64-linux-gnu` 等系统目录，
build.rs 找不到；用 deb 的话也要按下述手动拷进 `/usr/local/cuda`）：

```bash
tar -xzvf TensorRT-10.x.x.Linux.x86_64-gnu.cuda-12.x.tar.gz
sudo cp TensorRT-10.x.x/include/* /usr/local/cuda/include/
sudo cp -a TensorRT-10.x.x/lib/libnvinfer.so* /usr/local/cuda/lib/
sudo cp -a TensorRT-10.x.x/lib/libnvonnxparser.so* /usr/local/cuda/lib/
sudo ldconfig

cargo build -p katago --features trt --release
```

（Linux 链接的是不带版本后缀的 `libnvinfer.so`/`libnvonnxparser.so`，tarball 自带这两个
symlink，`cp -a` 会保留。）

### 4.4 验证与运行

```bash
./target/release/katago-rs gtp --config configs/gtp_trt.cfg --model /path/to/b11fix.onnx
```

首次启动会构建 TRT engine（较慢），并在模型旁缓存 `.trtplan` 文件，之后秒级启动。
如果启动即报 TRT 未启用/未编译，回看构建日志里是否有 §4.1 的 warning。

运行期还需 TRT 与 cudart 的动态库可被找到：Windows 靠上面拷进 `<CUDA>\bin` 的 DLL；
Linux 靠 ldconfig（或把 `/usr/local/cuda/lib` 加入 `LD_LIBRARY_PATH`）。

## 5. WSL2

WSL2 里编 CUDA 后端与原生 Linux 相同，另有现成一键脚本：

```bash
bash scripts/wsl_setup.sh    # apt 基础包 + rustup + wsl-ubuntu 源的 cuda-nvcc/cudart
```

要点：

- WSL 的 GPU 驱动由 Windows 宿主透传（`nvidia-smi` 可用），**WSL 内不要装驱动**；
  脚本装的是 wsl-ubuntu 专属 repo 的 nvcc/cudart。
- 脚本会把 `/usr/local/cuda/bin` 写入 root 的 `.profile`；手动装的话记得
  `export PATH=/usr/local/cuda/bin:$PATH`。
- CUDA 构建指纹（build fingerprint）区分平台：Windows 与 WSL 编出的二进制互不认对方的
  认证 tactic plan（`plans/best-tactic-plan-sm120-q64-wsl.json` 是 WSL 专用版）。
  跨平台复用 plan 会 fail-closed 启动失败，属预期行为。
- TRT 后端在 WSL 下按 §4.3 的 Linux 步骤走（主验证环境是 CUDA 后端）。

## 6. 常见问题速查

| 症状                                                                                                  | 原因                                                       | 处理                                                               |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------ |
| 构建 warning `nvcc not found`                                                                         | CUDA_PATH/CUDA_HOME/PATH 都没找到 nvcc                     | 装 CUDA Toolkit 或设 `CUDA_PATH`（Win）/`CUDA_HOME`（Linux）后重编 |
| 运行报 `no compiled SM target compatible with device capability X.Y`                                  | 你的 GPU 架构没编进二进制（nvcc 缺失或 sm-targets 未覆盖） | 按 §3.2 往 `configs/sm-targets.json` 加条目重编                    |
| nvcc 报 `unsupported gpu architecture '120'`                                                          | toolkit 低于 CUDA 12.8                                     | 升级 toolkit，或从 sm-targets 移除高架构目标                       |
| Windows 上 nvcc 找不到 cl.exe / 链接器报 link.exe 缺失                                                | 没装 VS C++ 工作负载                                       | 装 VS 2022 生成工具 + C++ 桌面开发（§1.1）                         |
| warning `CUTLASS not found`                                                                           | 没找到 CUTLASS                                             | 按 §3.4 克隆/设 `KATAGO_CUTLASS_ROOT`；不处理则少一个性能 tactic   |
| 构建直接失败：`nvcc -c failed for dual_ffn_cutlass`                                                   | cuda-host 源码/环境坏（fail-loud 设计）                    | 修环境；确需绕过设 `KATAGO_ALLOW_BROKEN_CUDA_HOST=1`               |
| warning `NvInfer.h not found … TensorRT shim skipped`                                                 | TRT 没并进 CUDA 目录                                       | 按 §4.1/4.2/4.3 拷贝头文件与库                                     |
| 链接错误 `nvinfer_10.lib`（LNK1104）/ `-lnvinfer`                                                     | 装的不是 TensorRT 10.x，或库没拷到位                       | 换 TRT 10.x 并确认库在 §4.1 的位置                                 |
| 编 TRT 报 `'platformHasFastFp16': is not a member of 'nvinfer1::IBuilder'` / `kEXPLICIT_BATCH` 未定义 | 头文件是 TensorRT 11（如 CUDA 13.x 目录里并入的新版 TRT）  | 换 TRT 10.x 的头/库重新并入（§4.1）                                |
| 启动报 plan 指纹/模型不匹配（fail-closed）                                                            | 认证 plan 与本机 GPU/模型/构建不符                         | 删配置里的 `cudaTacticPlan` 行，或重跑 `scripts/autotune.py`       |
| Linux 链接缺 `libssl`/`pkg-config` 报错                                                               | 基础包没装                                                 | `apt install pkg-config libssl-dev`                                |

## 7. 模型从哪来（真实推理需要，务必先读）

**这是编译之外最大的门槛**：模型不随仓库分发（被 gitignore），且三个后端认的格式不一样。

- **CUDA 后端（`cudabackend`）：只接受 KataGo 导出的 `.onnx` 文件。**
  验证范围是 b11c768h12nbt 系列（modelVersion 15，transformer 架构，opset 18；
  开发用的实例为 `b11fix.onnx`，305 MB、75M 参数）。从
  [katagotraining.org](https://katagotraining.org/networks/) 下载的是 KataGo **原生**
  `.bin.gz` 格式，CUDA 后端**不直接认**——需要先导出成 ONNX。仓库目前**不含**
  `.bin.gz → .onnx` 的导出工具（`b11fix.onnx` 是开发时用外部工具导出的），
  这是玩家侧的现实门槛：要么向项目维护者索取已导出的 ONNX，要么自行导出
  （需要与模型 opset 18 / 输入输出名一致的导出配置，非官方一键流程）。
- **TRT 后端（`trtbackend`）：`.onnx` 直接可用（验证口径）**；代码里也保留了
  原生 `.bin.gz` / `.txt.gz` / `.bin` / `.txt` 加载路径（进程内转 ONNX），但对较新
  b 系列 transformer 的原生解析存在未完全对齐的遗留问题，TRT 后端建议直接喂 `.onnx`。
- **dummy 后端**：`--model /dev/null` 即可，无需任何模型。
- 任意其它 ONNX/网络结构不保证兼容（仅 19 路、NCHW 输入：`input_spatial [B,22,19,19]`
  - `input_global [B,19]`，输出 v15 五组张量）。

编译完成后逐条验证：

```bash

# 4) CUDA/TRT：真实模型 GTP（模型路径替换后；CUDA 必须是 .onnx，见 §7）
./target/release/katago-rs gtp --config configs/gtp_smoke.cfg \
```
